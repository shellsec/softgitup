决策模型

System One / 结构化决策：给软件用的快决策层，不是聊天机器人。有闭源云 API，也有开源权重可自托管。

日常旗舰聊天与编码看 模型选型；Agent 编排看 Agent 横评；按量推理云看百科「AI 模型 API」。

最后更新：2026-09-23

这类模型是什么
决策模型（TypeSafe 称为 System One）面向程序调用：你传入状态（文本 / JSON），再声明若干固定题型，模型一次返回选择题、打分或是/否概率——带校准置信度，可直接写进分支逻辑。
  • 不做：聊天回复、写代码、写说明文、自由生成字符串。
  • 要做：分类、路由、紧急度打分、是否触发下一步、校验 LLM 输出是否可信。
  • 和「让 LLM 输出 JSON」不同：答案空间由调用方事先定死，格式上不会跑偏成散文。
闭源云 API Jev（TypeSafe） 开源权重 Laya（Apache 2.0）· NanoJev 聊天请用 LLM
和聊天 LLM 怎么选
决策模型（如 Jev）聊天 LLM（GPT / Claude / …）
输出 类型安全的选择 / 分数 / 概率 自然语言（也可约束成 JSON，但仍是生成文本）
适合 软件内大量重复的窄决策、低延迟分支 对话、写作、编码、开放式推理
不适合 需要人读的说明、代码、长文 要把答案当硬类型塞进代码且不能容忍格式幻觉时
常见用法 Agent / 工作流里的「快决策层」 主智能体、Copilot、内容生成

多数产品会两者并用：LLM 负责理解与生成，决策模型负责稳定、便宜的分拣与闸门。

Apache 2.0自托管需微调才强

和 Jev 的差别：权重可下、可再训、数据不出机房；不是托管 API。官方 model card 写明：基座 checkpoint 在 typed-decisions 上接近随机，0.766 那档是微调后的；出厂概率偏自信，上线前应用自己的数据做温度校准。多选项（如 50+ 标签）默认头预算偏紧，需调 head_max_len 或分层选择。目录见 systemonemodels.org（更新至 2026-09-22）。

如何使用

统一形态（与官方题型对齐，不是第三套 API）：context（程序状态 / 文本） + [question1, question2, …] → 每条题返回有界答案与概率。Jev / Laya 题型为 Choice / Score / Noul；NanoJev 为 Choice / Boolean / Score。上层拿概率做阈值、加权、路由，不靠模型吐 JSON。

托管 Jev 云 API

什么时候用：不想运维权重、要托管校准决策、把窄问题嵌进工作流 / Agent 闸门。

  1. 官方：Playground 试用 → Docs 拿 HTTP / Python / JS SDK 凭证；或已有 OpenRouter / Vercel AI Gateway 时改模型名为 typesafe/jev（OpenRouter）/ 对应 Gateway 标识。
  2. 输入：非结构化程序状态（文本 / 结构化字段）+ 事先定好的题（Choice / Score / Noul）。
  3. 输出：类型安全答案 + 校准概率 / 置信度；一次查询可并行多题；不生成自由文本。
  4. 上层怎么用：对「是否投诉 / 是否升级」等 Noul 设阈值；对 Choice 取最高概率分支；对 Score 做加权。Coding Agent 可装 typesafe-ai/skills，要求一次把歧义列成带选项的题。刊例与配额以官网为准。
自托管 Laya（生产向开源）

适合谁：数据不出机房、要可再训、可对标 Jev 请求形的本机 / 内网服务。

  1. 权重：HF convaiinnovations/laya；代码 / 说明：GitHub；pip install laya。
  2. 最短路径：Router(preload=True).predict(state, questions)；或 laya.load(...) 单 checkpoint。题型同 Jev：Choice / Score / Noul。
  3. 可选 pip install "laya[serve]" + laya-serve，HTTP 形与 TypeSafe System One 同形，换 base URL 即可。
  4. 官方写明：基座在 typed-decisions 上接近随机，强效果靠微调；出厂概率偏自信，上线前用自己的数据做温度校准。
研究复现 NanoJev（0.6B）

适合谁：学并行决策接口、小模型实验、对照迷宫 / 游戏环境。不是 Jev 商业替代。

  1. 权重：HF C-Tianyu/NanoJev（如 unified-games-v1）；仓库：TianyuCodings/NanoJev。
  2. 输入 state + questions（Choice / Boolean / Score）；输出候选分布 / yes-no 概率 / 有序分档概率——单次前向，不解码输出 token。
  3. 本地可用仓库脚本起推理服务；底座 Qwen3-0.6B，复杂推理与超长上下文别指望。
短例子（工单预审，用概率不当 JSON）： Context = 工单正文与元数据。Questions 例如：是否像投诉（Noul/Boolean）、是否紧急（Score 或 Noul）、是否该升级人工（Noul）。 返回每条 yes/no（或分档）概率后，上层写规则：投诉≥0.7 且紧急≥0.6 → 进投诉队列；升级≥0.75 → 转人工；否则自动分派。全文仍不生成客服回复——回复交给 LLM。

场景怎么用

每条：做什么判断 → 产出干什么。高风险域限制写死在块内，不当终审。

Agent
  • 下一步动作路由 → 选工具 / 子流程，替代 LLM 吐 JSON 再解析
  • 对话是否已可结束 / 是否需澄清 → 状态机跳转
  • 调用敏感工具前预检 → 权限闸门（低置信则拒或人工）
  • LLM 输出是否跑偏题 / 是否像幻觉 → 自检后再展示
  • 多 Agent 分派（谁处理）→ 固定候选人 Choice
  • 任务难度分流 → 简单改动走小模型、复杂重构才上大模型（如 Codex Router 思路）
  • 长任务上下文压缩 → 对工具调用日志做保留 / 丢弃打分（如 fast-jev-compaction）
  • 浏览器自动化 → 每步「点哪个 / 做什么」两组 Choice（如 jev-ultrafast）
  • Shell / 命令安全审查 → 危险命令特征分类后再执行
办公 / 客服
  • 工单多标签（投诉 / 退款 / 技术）→ 队列路由
  • 从十几个业务小组里选主管团队 → 取代脆弱正则（Choice）
  • 重复扣费 / 情绪激动 / 退款等高危客诉 → 毫秒级紧急度打标再推人工
  • 商业邮件意图分类 → 用校准概率设置信阈值（不必每次上大模型）
  • 客服质检：是否承诺法外权益、是否态度失控 → 抽检池
  • 合同 / 公文预审：是否缺签章页、是否含金额变更 → 标红给人核
  • 报销初审：票据与事由是否明显不符 → 退回补材料
  • 简历硬性条件（学历 / 年限 / 到岗）→ 筛入面试池
  • 文档是否像含密钥路径 / 身份证号特征 → 拦截外发
  • 会议纪要是否含待办 / 决策句 → 生成待办清单的前置打标
  • CI 里 PR 合并资格预审（改动清单 + 测试报告）→ 高风险打「待人工复查」
风控 · 内容特征
  • 告警文案是否像误报 → 降级或并入噪声队列
  • 评论 / 私信是否像广告灌水 → 进审核队列
  • 用户输入是否像越权索要（角色 / 权限）→ 拒绝或降权工具
  • 正文是否含敏感外链特征 → 标记人工看

只做文本特征预审 / 分级辅助。不写钓鱼制作、绕过、最终拦截规则实现；安全终审必须规则或人工。

教育 · 电商 · 内容
  • 作业是否跑题、题干是否歧义 → 退回重写（不是判分）
  • 评论多标签（物流 / 品质 / 客服）→ 归因看板
  • 售后初分：是否像质量问题 vs 使用问题 → 分流工单
  • 商家消息是否引导站外交易 → 违规预审
  • 稿件 / 脚本预审：是否缺事实出处、是否像广告植入 → 编辑队列
  • 新闻是否像突发事件 → 加急编排（仍要编辑确认）
医疗（非诊断）
  • 描述是否像急症表述 → 引导就医 / 紧急通道文案
  • 是否在索要处方 / 具体用药方案 → 拒答并转合规话术
  • 是否含自伤表述 → 危机资源引导（不代替危机干预）
  • 客服是否在给诊疗建议 → 质检下线

不能做疾病诊断、不能开处方。仅非诊断文本特征；终审与处置必须人工 / 合规流程。

法律 · 金融 · 研发
  • 合同条款是否像高风险（单方解约 / 无限责任）→ 律师预审队列（不能替代律师）
  • 咨询是否像在求「胜诉保证」→ 拒答并转人工法务
  • 贷款申请叙述是否像材料不全 → 补件提示（不能做信贷审批或投资建议）
  • 需求是否缺验收标准、Bug 是否像严重故障 → 排期 / P0 标签
  • 提交说明是否像带了密钥路径 → 拦截合并（不教如何藏密钥）

法律 / 信贷 / 投资结论只能当辅助特征，必须规则或持牌人工复核。

游戏 / 仿真 / 机器人
  • 环境文本观测上的局部布尔：NPC 是否可见威胁 → 行为树分支
  • 任务目标是否已满足 → 关卡结算前置
  • 仿真日志是否像异常态 → 重置或人工接管
  • 高频动作环（Doom / 跑酷 / 马里奥）：读状态 → Choice 出键位 / 走位
  • 卡牌 / 策略局：出牌、换牌等有界选项（文称可压到亚秒级单步）
  • 物理仿真窄决策：点火时机、姿态切换等（仍须仿真安全边界）

只做观测 / 状态上的布尔与选择；不写自动驾驶控制参数，也不当链上实盘交易引擎。

通用模板

  • Context：工单 / 对话 / 状态 JSON / 文档片段
  • Questions：多条固定题（Choice / Score / Noul 或 Boolean）
  • 输出：每条 yes 与 no（或选项）概率
  • 上层：阈值 + 加权打分 → 路由 / 闸门 / 打标

统一限制

  • 不生成自由文本
  • 诊断、信贷、法律判决、安全最终拦截：只能当辅助特征，必须规则或人工复核
  • NanoJev：0.6B，不适合强推理；上下文越长越易丢信息
  • 适合：前置预审、路由、可审计打分、本地轻量判断

和普通 LLM 怎么选

  • 要写文章 / 代码 / 摘要 / 对话 → 普通 LLM
  • 同一段文本批量做可审计 yes/no、避免 JSON 解析崩 → 这类决策模型
  • 常见组合：LLM 生成，决策模型做闸门与分拣
常见问题
能替代 Claude / GPT 写代码吗？▼
不能。决策模型不生成字符串。写代码、改仓库、解释结论仍用 LLM 或 Coding Agent。
开源和 Jev 怎么选？▼
要自托管 / 可再训 / 数据不出域 → Laya。要托管 API、少运维 → Jev（Early Access）。NanoJev 偏研究与小模型实验。不要拿冻结聊天模型的「OpenJev 式」脚本当生产决策引擎。
和「强制 JSON 输出」有何不同？▼
JSON mode 仍是自回归生成文本再解析；决策模型按题型出有界答案（常带概率）。适合闸门与路由，不适合写散文。
国内能直连 Jev 吗？▼
TypeSafe 为海外 Early Access，连通与开通以官网为准。已有 OpenRouter / Vercel AI Gateway 账号可优先走聚合层（OpenRouter 标识 typesafe/jev）。Laya / NanoJev 走 HF / GitHub 自托管，不依赖 TypeSafe 网络。
社区那二十多个玩法都要跟吗？▼
不必。先固定题型与阈值，再挑和自己业务同形的：分流 / 闸门 / 压缩 / 浏览器步进。游戏与链上演示验证吞吐与成本，不等于生产方案；高风险域仍须规则或人工终审。

一句话怎么用

要托管 API → Jev（闭源云）
要开源自托管 → Laya（Apache 2.0）
要小模型实验 → NanoJev
要聊天/编码 → 模型选型
